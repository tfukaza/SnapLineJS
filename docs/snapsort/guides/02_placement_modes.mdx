SnapSort offers several _modes_, selected per container with `config.mode`.
Each mode combines a target resolver with a form of placement feedback. What
follows the pointer is a separate per-session choice.

Drop policy runs before mode-specific placement. `canDrop` removes ineligible
containers, priority retains only the most preferred containers, and then the
mode ranks their remaining positions. When every priority is the default `0`,
the mode ranks all eligible positions globally. See
[Drop Policies](/docs/snapsort/guides/04_drop_policies).

> [!WARNING]
> Root container and all nested containers must have the same `mode` configured.

## Three Independent Decisions

Think about a drag as three independent axes:

| Concern                | Question                              | API                                                            |
| ---------------------- | ------------------------------------- | -------------------------------------------------------------- |
| Target resolution      | Which container and index wins?       | `config.mode`, eligibility, and priority callbacks             |
| Placement feedback     | How is that prospective result shown? | The mode's target ghost, insertion marker, or swap hover state |
| Pointer representation | What follows the pointer?             | `session.dragVisual`                                           |

`dragVisual` is `"item" | "preview" | "none"`:

- `"item"` moves the real rendered Items and creates source spacers where a
  mode needs to keep their old layout slots stable.
- `"preview"` leaves the Items in layout and creates one root-owned pointer
  `Ghost` for the complete ordered drag run.
- `"none"` leaves the Items in layout without a pointer-following visual.

Choose it while the session is pending, normally in the root's `onDragStart`:

```ts
import type { DragStartEvent } from "@snap-engine/snapsort";

function onDragStart(event: DragStartEvent) {
  event.session.dragVisual = "preview";
}
```

The value becomes fixed when activation begins. Built-in defaults preserve
each mode's familiar behavior: euclidean/progressive use `"item"`, insertion
uses `"none"`, and swap uses `"preview"`.

`dragVisual` never decides whether data changes. That remains
`session.dropEffect`: `"move"` commits the mode's normal mutation, while
`"none"` keeps target resolution and `onDragEnd` reporting but suppresses the
persistent move or swap callback. Unlike `dragVisual`, the drop effect may
change as the prospective target changes.

## Give a Drop Application Meaning

SnapSort resolves a destination; the application decides what that destination
means. A container with `metadata={{ role: "trash" }}` is still just a
Container to SnapSort. To implement drop-to-delete, suppress the ordinary move
while that destination is prospective, then delete from application state only
when `onDragEnd` reports it as the final destination:

```ts
import type {
  DragEndEvent,
  DropTargetChangeEvent,
  ItemId,
  RenderEntry,
  RenderTree,
} from "@snap-engine/snapsort";

function removeEntries<T>(
  tree: RenderTree<T>,
  deleted: ReadonlySet<ItemId>,
): RenderTree<T> {
  const entries: RenderEntry<T>[] = [];

  for (const entry of tree.entries) {
    if (entry.isGhost) {
      entries.push(entry);
    } else if (!deleted.has(entry.itemId)) {
      entries.push({
        ...entry,
        childTree: entry.childTree
          ? removeEntries(entry.childTree, deleted)
          : null,
      });
    }
  }

  return { ...tree, entries };
}

function onDropTargetChange(event: DropTargetChangeEvent) {
  const isTrash = event.current?.containerMetadata.role === "trash";
  event.session.dropEffect = isTrash ? "none" : "move";
  setTrashHighlighted(isTrash);
}

function onDragEnd(event: DragEndEvent) {
  setTrashHighlighted(false);
  if (event.destination?.containerMetadata.role !== "trash") return;

  updateTree((current) => removeEntries(current, new Set(event.itemIds)));
}
```

Here `setTrashHighlighted` and `updateTree` are application functions, not
SnapSort exports. In React, `updateTree` can be the functional form of a state
setter; in Svelte it can assign the returned root to a `$state.raw` variable.
An application may instead delete from its domain model and rebuild the same
RenderTree entries.

`dropEffect = "none"` tells SnapSort not to emit the ordinary item move or swap;
it does not mean “delete.” Checking `event.destination` rather than remembered
hover state makes cancellation safe because a cancelled drag reports
`destination === null`. Removing every `event.itemIds` entry makes the recipe
correct for a selected multi-item run. The recursive `removeEntries` function
is intentionally application-local: SnapSort does not assign delete semantics
to any container.

## Euclidean

Euclidean placement is the default mode (`mode: "euclidean"`, or omit `mode` entirely).
This is a simple nearest-neighbor algorithm that places the item at the location
with the closest center to the dragged item's center.

<PlacementModeDemo mode="euclidean" />

Euclidean placement is simple and direct, making it
suitable for most common drag and drop layouts:

- Kanban boards
- Vertical lists
- Grid layouts
- etc.

Its target feedback is a full-size `type: "target-spacer"` ghost that moves
through whichever container owns the current prospective slot. With the default
`"item"` visual, the dragged Items themselves follow the pointer. A valid move
dispatches to the root's `onItemMove` callback, or its root-level `onItemInsert`
fallback; the event payload identifies the direct destination.

## Insertion

Insertion placement (`mode: "insertion"`) replaces the full-size
ghost with a thin floating marker line that shows where the
item will be inserted after drop. The item itself
stays in its original DOM position until drop.

SnapSort builds physical gap lines from the frozen layout between Items and
Container Items. After `canDrop` and effective priority filter the eligible
containers, insertion ranks those lines by strict Euclidean distance from the
pointer to each line's center. The visible marker is derived only after a gap
wins, so marker thickness, color, and visual insets never influence targeting.

Nested containers participate through their real layout geometry. For example,
a file explorer can physically inset and narrow a folder's child Container;
the child gaps then have centers farther to the right and naturally win as the
pointer moves into that region. SnapSort does not add a hidden “prefer the
deepest container” rule. When two candidates have the exact same center,
distance to their adjacent Item rectangles breaks the tie; a remaining tie
keeps stable tree and gap order. An empty container has no synthetic adjacent
rectangle, so equal empty-gap centers also keep that stable order.

For a wrap-capable row, each gap spans the frozen measured row band, even when
the snapshot currently contains only one row. Once multiple rows are measured,
the gap uses the band of the visual row containing its chosen boundary. A
`wrap: "nowrap"` row instead spans the full container content height.

The `type: "insertion-marker"` ghost is located in the prospective target, while
a valid move mutation is dispatched to the root. The event payload identifies
the direct destination. The default `"none"` visual keeps the original rows
still without adding another pointer-following element.

<PlacementModeDemo mode="insertion" dragVisual="preview" />

This demo deliberately overrides insertion's default. The card following the
pointer is one root-owned Ghost with `type: "pointer-preview"`, while the thin
line is a Ghost located in the destination with `type: "insertion-marker"`.
Both are part of the same foundational ghost system.

An insertion marker carries a zero-thickness, world-space `gap`, the frozen
`previous` and `next` neighbors beside the chosen physical boundary, and
`isCurrentPlacement`. The last field means a normal move commit would leave the
complete dragged run where it already is; it is independent of `dropEffect`.
For a dragged Item's current placement, the leading and trailing outer lines
map to the same logical destination. Moving across the Item can therefore move
the marker from one edge to the other without changing the target index or
firing `onItemMove`.

Use Insertion placement for line-marker UIs:

- File/folder trees and outlines
- Nested, collapsible structures
- Any list where a full-size ghost reflowing sibling items would be visually noisy

## Swap

Swap placement (`mode: "swap"`) keeps the original item in its slot
during the drag and shows a pointer ghost as the visual preview.
The target is the item under the pointer; on drop, SnapSort swaps
the dragged item with that target. The pointer ghost has
`type: "pointer-preview"` and is owned by the root, item hit-testing is scoped
to the currently resolved target container, and hover callbacks run on the
direct owner of the item under the pointer. The final `onItemSwap` is dispatched
to the root; `event.a` and `event.b` identify both direct, pre-swap slots.

<PlacementModeDemo mode="swap" />

Swap uses `"preview"` by default, but its target selection and final
`onItemSwap` commit remain the same if another drag visual is chosen.

## Progressive

Progressive placement (`mode: "progressive"`) is designed for ordered,
variable-size items. Instead of a nearest neighbor approach, it treats
the layout as a progression of placement regions and chooses the first
region occupied by the dragged item's center.

It uses the same flow target feedback, `"item"` visual default, and
root-dispatched move commit as euclidean mode.

The difference is most noticeable if you take an item from the top row
in the above demo and move it around in the second row. Notice that
in the Euclidean version, sometimes the item's ghost may jump back
to the top, because mathematically speaking that is the closest possible
location the item can be dropped given the current position of the item.
As humans we're trained to read text from top left to bottom right,
so this feels unnatural. The progressive algorithm is specifically designed
to take that perception into account.

## Build Copying from a Move

Copying does not require a special drag lifecycle. Treat it as an ordinary
move and synchronously backfill the vacated source in `onItemMove`:

```ts
function copyByMoving(event: ItemMoveEvent) {
  updateLists((lists) => {
    const original = removeById(lists, event.itemId);
    if (!original) return lists;

    insertAt(lists, event.to, original);
    const source =
      event.from.container === event.to.container &&
      event.to.index < event.from.index
        ? { ...event.from, index: event.from.index + 1 }
        : event.from;
    insertAt(lists, source, {
      ...original,
      id: crypto.randomUUID(),
    });
    return lists;
  });
}
```

This compact recipe assumes a single-item drag. If the interface enables
multi-selection, either reject copy for a multi-item session or implement the
same operation for the complete ordered `event.itemIds`/`event.froms` run; do
not backfill only the primary item.

The original stable ID moves to the destination, so the thing the user
dragged is also the thing that performs the drop animation. The fresh source
replacement has no pre-mutation rectangle; SnapSort's FLIP pass ignores it
instead of trying to inverse-animate it. Use application metadata to decide
which sources should use this recipe, and set `dragVisual = "preview"` if the
source should remain visually occupied while dragging.

The same-container adjustment preserves the vacated source slot when the
original moves toward a lower index: inserting the original before that slot
shifts the slot one position to the right before the replacement is added.

For lower-level interfaces that mount a replacement run as a drag begins,
`DragSession.handoff(replacements)` transfers pointer ownership and frozen
drag geometry to that already-mounted parallel run. Call it while the session
is pending in `onDragStart`; lifecycle activation locks it afterward. It is
intentionally copy-neutral: it does not create state, render components, or
clean up either run.

### Migrating from built-in copy

If an earlier implementation used `session.dropEffect = "copy"` and
`onDragClone`:

1. Remove the clone callback and transient adopted-Item state.
2. Optionally set `session.dragVisual = "preview"` in `onDragStart`.
3. Let the root receive a normal `onItemMove`; its non-null `from` and `to`
   locations identify the source and destination.
4. Move that original ID to `to` and mint the replacement ID at `from` in one
   synchronous state update.
5. Remove clone-cancellation `onItemRemove` cleanup and any reads of the former
   `origin*` provenance fields.

Do not swap the identities: keeping the old ID at the source and minting a new
destination ID disconnects the dragged visual from its drop-animation target.
