SnapSort offers several _modes_, selected per container with `config.mode`.
Each mode combines a target resolver with a form of placement feedback. What
follows the pointer is a separate per-session choice.

Drop policy runs before mode-specific placement. `canDrop` removes ineligible
containers, priority retains only the most preferred containers, and then the
mode ranks their remaining positions. When every priority is the default `0`,
the mode ranks all eligible positions globally. See
[Drop Policies](/docs/snapsort/guides/04_drop_policies).

> [!WARNING]
> Root container and all nested containers must have the same `mode` configured.

## Three Independent Decisions

Think about a drag as three independent axes:

| Concern                | Question                              | API                                                            |
| ---------------------- | ------------------------------------- | -------------------------------------------------------------- |
| Target resolution      | Which container and index wins?       | `config.mode`, eligibility, and priority callbacks             |
| Placement feedback     | How is that prospective result shown? | The mode's target ghost, insertion marker, or swap hover state |
| Pointer representation | What follows the pointer?             | `session.dragVisual`                                           |

`dragVisual` is `"item" | "preview" | "none"`:

- `"item"` moves the real rendered Items and creates source spacers where a
  mode needs to keep their old layout slots stable.
- `"preview"` leaves the Items in layout and creates one root-owned pointer
  `Ghost` for the complete ordered drag run.
- `"none"` leaves the Items in layout without a pointer-following visual.

Choose it while the session is pending, normally in the root's `onDragStart`:

```ts
import type { DragStartEvent } from "@snap-engine/snapsort";

function onDragStart(event: DragStartEvent) {
  event.session.dragVisual = "preview";
}
```

The value becomes fixed when activation begins. Built-in defaults preserve
each mode's familiar behavior: euclidean/progressive use `"item"`, insertion
uses `"none"`, and swap uses `"preview"`.

`dragVisual` never decides whether data changes. That remains
`session.dropEffect`: `"move"` commits the mode's normal mutation, while
`"none"` keeps target resolution and `onDragEnd` reporting but suppresses the
persistent move or swap callback. Unlike `dragVisual`, the drop effect may
change as the prospective target changes.

## Euclidean

Euclidean placement is the default mode (`mode: "euclidean"`, or omit `mode` entirely).
This is a simple nearest-neighbor algorithm that places the item at the location
with the closest center to the dragged item's center.

<PlacementModeDemo mode="euclidean" />

Euclidean placement is simple and direct, making it
suitable for most common drag and drop layouts:

- Kanban boards
- Vertical lists
- Grid layouts
- etc.

Its target feedback is a full-size flow ghost that moves through whichever
container owns the current prospective slot. With the default `"item"` visual,
the dragged Items themselves follow the pointer. A valid move commits through
the direct destination.

## Insertion

Insertion placement (`mode: "insertion"`) replaces the full-size
ghost with a thin floating marker line that shows where the
item will be inserted after drop. The item itself
stays in its original DOM position until drop.

The marker is owned by the prospective target, while a valid move mutation is
received by the direct destination. The default `"none"` visual keeps the
original rows still without adding another pointer-following element.

<PlacementModeDemo mode="insertion" dragVisual="preview" />

This demo deliberately overrides insertion's default. The card following the
pointer is one root-owned `kind: "marker", role: "pointer"` Ghost, while the
thin line is the destination-owned `kind: "marker", role: "target"` Ghost.
Both are part of the same foundational ghost system.

Use Insertion placement for line-marker UIs:

- File/folder trees and outlines
- Nested, collapsible structures
- Any list where a full-size ghost reflowing sibling items would be visually noisy

## Swap

Swap placement (`mode: "swap"`) keeps the original item in its slot
during the drag and shows a pointer ghost as the visual preview.
The target is the item under the pointer; on drop, SnapSort swaps
the dragged item with that target. The pointer ghost is owned by the root,
item hit-testing is scoped to the currently resolved target container, and
hover callbacks run on the direct owner of the item under the pointer. The
final `onItemSwap` runs on the dragged item's direct, pre-swap source.

<PlacementModeDemo mode="swap" />

Swap uses `"preview"` by default, but its target selection and final
`onItemSwap` commit remain the same if another drag visual is chosen.

## Progressive

Progressive placement (`mode: "progressive"`) is designed for ordered,
variable-size items. Instead of a nearest neighbor approach, it treats
the layout as a progression of placement regions and chooses the first
region occupied by the dragged item's center.

It uses the same flow target feedback, `"item"` visual default, and
destination-owned move commit as euclidean mode.

The difference is most noticeable if you take an item from the top row
in the above demo and move it around in the second row. Notice that
in the Euclidean version, sometimes the item's ghost may jump back
to the top, because mathematically speaking that is the closest possible
location the item can be dropped given the current position of the item.
As humans we're trained to read text from top left to bottom right,
so this feels unnatural. The progressive algorithm is specifically designed
to take that perception into account.

## Build Copying from a Move

Copying does not require a special drag lifecycle. Treat it as an ordinary
move and synchronously backfill the vacated source in `onItemMove`:

```ts
function copyByMoving(event: ItemMoveEvent) {
  updateLists((lists) => {
    const original = removeById(lists, event.itemId);
    if (!original) return lists;

    insertAt(lists, event.to, original);
    insertAt(lists, event.from, {
      ...original,
      id: crypto.randomUUID(),
    });
    return lists;
  });
}
```

The original stable ID moves to the destination, so the thing the user
dragged is also the thing that performs the drop animation. The fresh source
replacement has no pre-mutation rectangle; SnapSort's FLIP pass ignores it
instead of trying to inverse-animate it. Use application metadata to decide
which sources should use this recipe, and set `dragVisual = "preview"` if the
source should remain visually occupied while dragging.

For lower-level interfaces that mount a replacement run as a drag begins,
`DragSession.handoff(replacements)` transfers pointer ownership and frozen
drag geometry to that already-mounted parallel run. Call it while the session
is pending in `onDragStart`; lifecycle activation locks it afterward. It is
intentionally copy-neutral: it does not create state, render components, or
clean up either run.

### Migrating from built-in copy

If an earlier implementation used `session.dropEffect = "copy"` and
`onDragClone`:

1. Remove the clone callback and transient adopted-Item state.
2. Optionally set `session.dragVisual = "preview"` in `onDragStart`.
3. Let the destination receive a normal `onItemMove` with non-null `from`.
4. Move that original ID to `to` and mint the replacement ID at `from` in one
   synchronous state update.
5. Remove clone-cancellation `onItemRemove` cleanup and any reads of the former
   `origin*` provenance fields.

Do not swap the identities: keeping the old ID at the source and minting a new
destination ID disconnects the dragged visual from its drop-animation target.
