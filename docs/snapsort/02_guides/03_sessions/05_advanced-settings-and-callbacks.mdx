The placement mode is only one part of a drag. Session settings control what
follows the pointer and whether SnapSort commits its ordinary mutation, while
callbacks let the application attach domain behavior to the resolved result.

## Three Independent Decisions

Think about a drag as three independent axes:

| Concern                | Question                              | API                                                            |
| ---------------------- | ------------------------------------- | -------------------------------------------------------------- |
| Target resolution      | Which Container and index wins?       | `config.mode`, eligibility, and priority callbacks             |
| Placement feedback     | How is that prospective result shown? | The mode's target ghost, insertion marker, or swap hover state |
| Pointer representation | What follows the pointer?             | `session.dragVisual`                                           |

`dragVisual` is `"item" | "preview" | "none"`:

- `"item"` moves the real rendered Items and creates source spacers where a
  mode needs to keep their old layout slots stable.
- `"preview"` leaves the Items in layout and creates one root-owned pointer
  Ghost for the complete ordered drag run.
- `"none"` leaves the Items in layout without a pointer-following visual.

`"none"` does not disable drop animation. When a drop animation is configured,
the retained Items animate from their visible pre-commit positions to their
committed positions.

Choose it while the session is pending, normally in the root's `onDragStart`:

```ts
import type { DragStartEvent } from "@snap-engine/snapsort";

function onDragStart(event: DragStartEvent) {
  event.session.dragVisual = "preview";
}
```

The value becomes fixed when activation begins. Built-in defaults preserve
each mode's expected behavior: euclidean and progressive use `"item"`,
insertion uses `"none"`, and swap uses `"preview"`.

`dragVisual` never decides whether application data changes. That remains
`session.dropEffect`: `"move"` commits the mode's normal mutation, while
`"none"` keeps target resolution and `onDragEnd` reporting but suppresses the
persistent move or swap callback. Unlike `dragVisual`, the drop effect may
change while the session is active and the prospective target changes.

## Give a Drop Application Meaning

SnapSort resolves a destination; the application decides what that destination
means. A Container with `metadata={{ role: "trash" }}` is still just a
Container to SnapSort. To implement drop-to-delete, suppress the ordinary move
while that destination is prospective, then delete from application state only
when `onDragEnd` reports it as the final destination:

```ts
import type {
  DragEndEvent,
  DropTargetChangeEvent,
  ItemId,
  RenderEntry,
  RenderTree,
} from "@snap-engine/snapsort";

function removeEntries<T>(
  tree: RenderTree<T>,
  deleted: ReadonlySet<ItemId>,
): RenderTree<T> {
  const entries: RenderEntry<T>[] = [];

  for (const entry of tree.entries) {
    if (entry.isGhost) {
      entries.push(entry);
    } else if (!deleted.has(entry.itemId)) {
      entries.push({
        ...entry,
        childTree: entry.childTree
          ? removeEntries(entry.childTree, deleted)
          : null,
      });
    }
  }

  return { ...tree, entries };
}

function onDropTargetChange(event: DropTargetChangeEvent) {
  const isTrash = event.current?.containerMetadata.role === "trash";
  event.session.dropEffect = isTrash ? "none" : "move";
  setTrashHighlighted(isTrash);
}

function onDragEnd(event: DragEndEvent) {
  setTrashHighlighted(false);
  if (event.destination?.containerMetadata.role !== "trash") return;

  updateTree((current) => removeEntries(current, new Set(event.itemIds)));
}
```

Here `setTrashHighlighted` and `updateTree` are application functions, not
SnapSort exports. In React, `updateTree` can be the functional form of a state
setter; in Svelte it can assign the returned root to a `$state.raw` variable.
An application may instead delete from its domain model and rebuild the same
render entries.

`dropEffect = "none"` means “do not emit the ordinary move or swap”; it does
not mean “delete.” Checking `event.destination` rather than remembered hover
state makes cancellation safe because a cancelled drag reports
`destination === null`. Removing every `event.itemIds` entry handles a
selected multi-item run. The recursive `removeEntries` function is
intentionally application-local because SnapSort does not assign delete
semantics to any Container.

## Callback Ownership and Timing

Callbacks follow two routing rules. Anything that mutates or renders
application or ghost state is resolved on the root Container, with the root
adapter as a structural fallback. Policy, geometry, and hover callbacks are
read directly from the candidate Container or Item owner they inspect.

| Callback group                                         | Receiver                            | When it runs                                                                                        |
| ------------------------------------------------------ | ----------------------------------- | --------------------------------------------------------------------------------------------------- |
| `onDragStart`                                          | Root                                | Once while the session is pending; returning `false` vetoes startup.                                |
| `canDrop`, `getDropPriority`                           | Each candidate destination          | During target resolution; priority runs only after eligibility accepts that Container.              |
| `getItemHitbox`                                        | Direct owner of the hover candidate | Synchronously while SnapSort calculates that Item's world-space hitbox.                             |
| `onDragItemEnter`, `onDragItemMove`, `onDragItemLeave` | Direct owner of the hovered Item    | As pointer hit-testing begins, continues, or ends inside the currently resolved target Container.   |
| `onDropTargetChange`                                   | Root                                | When the prospective direct Container or logical index changes.                                     |
| `onGhostInsert`, `onGhostMove`, `onGhostRemove`        | Root                                | Synchronously when session-owned render state becomes present, changes, or becomes absent.          |
| `onItemMove`                                           | Root                                | When a move-mode drop or programmatic move command commits its semantic persistent mutation.        |
| `onItemSwap`                                           | Root                                | When a swap-mode drop commits one pairwise exchange.                                                |
| `onItemInsert`, `onItemRemove`                         | Root                                | For lower-level core insert/remove commands; insert also serves as the move fallback.               |
| `onDragEnd`                                            | Root                                | After any activated session finishes and clears its transient state, including `dropEffect="none"`. |
| `onVisualGeometryInvalidated`                          | Root                                | At most once per engine frame when transient Item geometry may need external invalidation.          |

An insertion marker can change physical `gap` presentation while its logical
Container and index remain the same. That produces `onGhostMove`, with equal
`from` and `to` locations, but not `onDropTargetChange`.

Structural callbacks run inside the adapter's synchronous commit boundary.
Framework callbacks must publish their next render state before returning;
they must not directly rearrange framework-owned DOM nodes.

## Build Copying from a Move

Copying does not require a special drop effect. Treat it as an ordinary move
and synchronously backfill the vacated source in `onItemMove`:

```ts
import type { ItemMoveEvent } from "@snap-engine/snapsort";

function copyByMoving(event: ItemMoveEvent) {
  updateLists((lists) => {
    const original = removeById(lists, event.itemId);
    if (!original) return lists;

    insertAt(lists, event.to, original);
    const source =
      event.from.container === event.to.container &&
      event.to.index < event.from.index
        ? { ...event.from, index: event.from.index + 1 }
        : event.from;
    insertAt(lists, source, {
      ...original,
      id: crypto.randomUUID(),
    });
    return lists;
  });
}
```

`updateLists`, `removeById`, and `insertAt` are application state helpers, not
SnapSort exports. They must perform this removal, destination insertion, and
source backfill as one synchronous framework-state update.

This compact recipe assumes a single-item drag. If the interface enables
multi-selection, either reject copy for a multi-item session or apply the same
operation to the complete ordered `event.itemIds` and `event.froms` run. Do
not backfill only the primary Item.

The original stable ID moves to the destination, so the thing the user dragged
is also the thing that performs the drop animation. The fresh source
replacement has no pre-mutation rectangle; SnapSort's FLIP pass ignores it
instead of trying to inverse-animate it. Use application metadata to decide
which sources use this recipe, and set `dragVisual = "preview"` if the source
should remain visually occupied during the gesture.

The same-Container adjustment preserves the vacated source slot when the
original moves toward a lower index: inserting the original before that slot
shifts the slot one position to the right before the replacement is added.

### Migrating from built-in copy

If an earlier implementation used `session.dropEffect = "copy"` and
`onDragClone`:

1. Remove the clone callback and transient adopted-Item state.
2. Optionally set `session.dragVisual = "preview"` in `onDragStart`.
3. Let the root receive a normal `onItemMove`; its non-null `from` and `to`
   locations identify the source and destination.
4. Move that original ID to `to` and mint the replacement ID at `from` in one
   synchronous state update.
5. Remove clone-cancellation `onItemRemove` cleanup and any reads of the former
   `origin*` provenance fields.

Do not swap the identities: keeping the old ID at the source and minting a new
destination ID disconnects the dragged visual from its drop-animation target.

Continue with [Drop Policies](/docs/snapsort/guides/sessions/drop-policies) for
destination eligibility and priority.
