SnapSort separates _whether_ a container accepts a drag, _which_ eligible
container should be preferred, and _where_ inside that container the item
should be placed. Applications express the first two decisions with metadata
and callbacks while the selected placement mode owns the last one.

## Resolution Order

Each built-in SnapSort mode resolves a prospective target in this order:

1. Generate the active mode's candidate positions and group them by their
   directly owning container.
2. Invoke each destination's `canDrop` once. Returning `false` removes every
   candidate owned directly by that container.
3. Start with the container's configured `dropPriority`, then invoke
   `getDropPriority` once. A returned number replaces the configured value;
   `undefined` preserves it.
4. Keep only candidates tied at the highest priority.
5. Let the active mode rank that remaining candidate set and choose the exact
   container and index.

The default `dropPriority` is `0`. When every eligible container stays at that
value, the placement mode ranks their positions globally just as it does in a
single list. Equal-priority containers also remain in the same global ranking.

Priority belongs only to positions directly owned by the configured container;
it does not propagate into nested containers. Negative and fractional values
are valid preferences. Configured or returned values must be finite numbers.
Use `canDrop`, not a special priority value, when a destination must be
ineligible.

## Define Eligibility with Metadata

SnapSort does not assign application meaning to a container. Put your own
domain identifiers in metadata and compare them in the destination-owned
`canDrop` callback. This example permits moves only between containers whose
application-defined `boardId` matches:

```ts
import type { CanDropEvent } from "@snap-engine/snapsort";

export function canDropInSameBoard(event: CanDropEvent): boolean {
  const boardId = event.containerMetadata.boardId;
  return (
    typeof boardId === "string" &&
    event.sources.every(
      (source) => source?.containerMetadata.boardId === boardId,
    )
  );
}
```

Assign `{ boardId }` to each container's `metadata` prop and include
`canDrop: canDropInSameBoard` in each destination's callbacks. `source` is the
primary dragged item's original `DragLocation`; `sources` is the parallel list
for the complete multi-item drag. A source may be `null` for a spawned item.

Item metadata is available too. Use `itemMetadata` for the primary item or
`itemsMetadata` for the complete ordered drag run. For example, a destination
can compare `event.containerMetadata.accepts` with a consumer-defined `kind`
on every entry in `event.itemsMetadata`.

`canDrop` runs once per container rather than once per candidate slot. Its
`index` therefore represents the first candidate evaluated for that container
and must not be used for per-position eligibility.

## Prefer a Container

Set a stable preference with `dropPriority`:

```svelte framework=Svelte
<Container
  itemId="words-root"
  metadata={{ boardId: "sentence" }}
  config={{ dropPriority: 2, callbacks }}
>
  {#each words.entries as entry (entry.itemId)}
    {#if entry.isGhost}
      <Ghost ghost={entry.ghost} />
    {:else if entry.childTree}
      <WordContainer {entry} />
    {:else}
      <Item itemId={entry.itemId}>{entry.value.label}</Item>
    {/if}
  {/each}
</Container>
```

```tsx framework=React
<Container
  itemId="words-root"
  metadata={{ boardId: "sentence" }}
  config={{ dropPriority: 2, callbacks }}
>
  {words.entries.map((entry) =>
    entry.isGhost ? (
      <Ghost key={entry.itemId} ghost={entry.ghost} />
    ) : entry.childTree ? (
      <WordContainer key={entry.itemId} entry={entry} />
    ) : (
      <Item key={entry.itemId} itemId={entry.itemId}>
        {entry.value.label}
      </Item>
    ),
  )}
</Container>
```

`WordContainer` is the recursive nested-Container branch: it renders the
entry's `childTree` and uses `entry.itemId` as the Container's `itemId`. Flat
word lists never enter that branch, but keeping the
three-way renderer makes the same component safe for nested data.

Use `getDropPriority` when preference depends on the current drag:

```ts
import type { DropPriorityEvent } from "@snap-engine/snapsort";

function prioritizeUrgentItems(event: DropPriorityEvent) {
  return event.itemsMetadata.every((metadata) => metadata.urgent === true)
    ? event.staticPriority + 1
    : undefined;
}
```

`DropPriorityEvent` includes the same item, source, and destination fields as
the eligibility event, plus:

| Field                  | Description                                                      |
| ---------------------- | ---------------------------------------------------------------- |
| `staticPriority`       | The destination's configured `dropPriority` before the callback. |
| `pointer`              | Current pointer position in world coordinates.                   |
| `dragRect`             | Current world-space rectangle of the primary dragged item.       |
| `containerRect`        | Frozen world-space border box of the destination.                |
| `containerContentRect` | Frozen world-space content box of the destination.               |
| `depth`                | Destination depth in the SnapSort tree.                          |

The callback runs only after `canDrop` accepts the destination. Returning a
number is an absolute override, so use `event.staticPriority` explicitly when
the configured value should contribute to the result.

## Standard Callbacks

Import common, pure policies from `@snap-engine/snapsort/callbacks`:

The geometry policies use SnapEngine's core collision primitives, keeping
containment, intersection, and edge-distance behavior consistent with the
collision engine.

| Callback                          | Behavior                                                                                                      |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `prioritizePointerContainer`      | Returns `1` when `containerRect` contains the pointer; otherwise preserves static priority.                   |
| `prioritizeIntersectingContainer` | Returns `1` when the primary `dragRect` intersects `containerRect`; otherwise preserves static priority.      |
| `prioritizeNearestContainerEdge`  | Returns the negative pointer-to-container distance; a pointer inside scores `0`.                              |
| `rejectDrop`                      | Always returns `false`; use it as `canDrop` for a structural container that must never accept items directly. |

```ts
import { prioritizePointerContainer } from "@snap-engine/snapsort/callbacks";

const callbacks = {
  ...mutationCallbacks,
  getDropPriority: prioritizePointerContainer,
};
```

The geometry helpers prefer containers before Euclidean, progressive,
insertion, or swap placement ranks positions. This is useful when differently
sized sibling zones make global position proximity a poor signal for the
destination the user intends.

## Programmatic Moves

`container.moveItem(id, targetContainer, index)` is an authoritative
application command. It bypasses `canDrop`, `dropPriority`, and
`getDropPriority`, then commits through the normal mutation callbacks. Validate
button, keyboard, or other programmatic actions in application code when they
should follow the same domain policy as pointer drops.

Adding or deleting application data is different: update framework state
directly and let reconciliation mount or unmount the corresponding Item. If
code deliberately invokes the core `container.removeItem(id)` command instead,
configure root `onItemRemove` and synchronize the application collection from
that event. A metadata role such as `"trash"` never gives SnapSort delete
semantics; see [Placement Modes](/docs/snapsort/guides/02_placement_modes#give-a-drop-application-meaning)
for the application-owned drop-to-delete recipe.
