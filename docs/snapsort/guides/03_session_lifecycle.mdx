When an item is dragged, SnapSort creates one internal session controller for
the root container. It exposes a stable, read-only `DragSession` handle through
callbacks and `root.dragSession`, follows the pointer, resolves prospective
destinations, owns temporary ghosts, and invokes callbacks on the container
tree root for structural commits. Candidate containers still own their local
drop policy, geometry, and hover callbacks; event locations identify the direct
source, destination, or ghost owner involved in each root-dispatched commit.

## Terms

- **Root / DragSession:** the top-level container and its public session handle.
  SnapSort's internal controller orchestrates target resolution, ghost
  relocation, commits, and cleanup.
- **Source Container:** an item's direct parent when the drag begins. In the
  diagram this lane also represents the current owner for operations such as
  ghost or item removal.
- **Target Container:** the prospective direct container and index selected while the
  pointer moves.
- **Destination Container:** the final direct container and index reported when the drag
  ends. It may be the source again, or `null` when the lifecycle ends without a
  resolved destination.
- **Ghost Item:** passive placeholder data managed by the lifecycle. A ghost
  does not ask to insert or remove itself.

## State Ownership

SnapSort callbacks report changes that SnapSort originates. A committed item
move is one semantic operation, even across containers, so the root receives
one `onItemMove` event for the complete ordered run. It does not also receive
`onItemRemove` for the source and `onItemInsert` for the destination.

Ghosts are different because their very presence is session-owned. The root
receives explicit `onGhostInsert`, `onGhostMove`, and `onGhostRemove` events so
framework state can render the same keyed ghost throughout its lifetime. An
application may pass all three to one `reduceRenderTree` handler without
collapsing the public callback contract. `onGhostMove` can also carry an
insertion marker's changed physical gap with equal `from` and `to` locations;
that visual update does not imply a changed drop target.

Application-originated additions and deletions do not need to round-trip
through these hooks. Update the application collection directly and let the
framework mount or unmount the corresponding SnapSort component. If application
code instead calls the imperative core command `container.removeItem(id)`, that
command emits root `onItemRemove`; a `RenderTree` consumer must apply it with
`reduceRenderTree` synchronously.

`onItemInsert` remains a lower-level primitive and the fallback when a root has
no `onItemMove`. It is intentionally outside `RenderTreeEvent`: its payload
identifies the core Item and location but cannot supply the application's value
for that new entry.
