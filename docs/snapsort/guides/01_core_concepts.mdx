SnapSort models a drag-and-drop interface with two primitives:
_items_ represent the things that can move, and
_containers_ define where things can be placed.

<SnapSortConceptsDiagram />

## Items Are Movable Elements

<SnapSortEntityCue kind="item" />

An `Item` is an UI element that can be dragged and placed in different locations.

Each item carries an `itemId`, which helps the library identify it even after it
moves. The developer must keep that ID stable for the item's lifetime and unique
within one SnapSort root. Independent roots may reuse the same IDs; a framework
`RenderTree` represents one such root.

## Containers Define Placement

<SnapSortEntityCue kind="container" />

A `Container` represents a region that can hold an ordered set of items.
Containers themselves are also considered an item, so it can be placed within
other container as well. That also means containers must also maintain an `itemId`.

For every drag-and-drop interface, there is always a single _root container_
that serves as the top-level parent for all draggable items and containers.
Containers that need to exchange items must be descendants of that same root.
Within the tree, the application decides which destinations are compatible by
putting its own identifiers on item or container metadata and inspecting them
in a destination's `canDrop` callback. Separate root trees never exchange items.

Eligibility and preference are separate. After `canDrop` rejects incompatible
containers, `dropPriority` and `getDropPriority` can prefer one destination
before the active placement mode chooses an exact position. See
[Drop Policies](/docs/snapsort/guides/04_drop_policies) for the complete order.

Callbacks follow two ownership rules. Structural mutations and root lifecycle
events are configured on and dispatched to the tree root; their event payloads
identify the semantic source, destination, and ghost owner. If a structural
callback is absent there, SnapSort falls back to the root adapter. Drop policy,
geometry, and hover callbacks remain local to the candidate destination or
direct item owner that they inspect. See
[Session Lifecycle](/docs/snapsort/guides/03_session_lifecycle) for the complete
routing table.

This does not make SnapSort the owner of application CRUD. An Add button or
Delete button changes application state directly, and the framework mounts or
unmounts the matching `Item`. Structural callbacks exist for the opposite
direction: they tell the application when a SnapSort command or drag has
already changed the core tree. Application-specific meanings such as “dropping
here deletes these records” belong in application lifecycle handlers.

> [!WARNING]
> Root containers must never be destroyed during the lifetime of the application,
> since they are responsible for maintaining the state of the entire drag-and-drop system.

## Ghosts Represent Temporary Visuals

<SnapSortEntityCue kind="ghost" />

Ghosts are passive, temporary visuals owned by a drag session. The exact
`GhostState.type` explains each ghost's job:

- `source-spacer` preserves a layout slot vacated by an actual dragged item.
- `target-spacer` previews a prospective full-size flow placement.
- `insertion-marker` previews a prospective placement as a marker line. Its
  zero-thickness `gap` is placement geometry; `previous`, `next`, and
  `isCurrentPlacement` explain the physical boundary SnapSort selected.
- `pointer-preview` follows the pointer without becoming application data.

A placement mode can use more than one at once. For example, insertion mode
can show an `insertion-marker` while a separate `pointer-preview` follows the
drag. Framework `RenderTree` state stores ghosts in the same keyed `entries`
sequences as ordinary values, and the application decides how each type looks
through its framework's `Ghost` rendering API.

Insertion marker state deliberately separates targeting from paint. SnapSort
ranks the immutable, world-space `gap`; the renderer turns that gap into a
visible rectangle with an explicit thickness and optional insets. Changing the
painted line does not change which gap wins.

Ghosts still need three structural callbacks because SnapSort owns their whole
presence lifecycle: it can insert a new ghost, move the same keyed ghost, or
remove it. Those callbacks remain explicit even when all three delegate to one
`reduceRenderTree` function. An ordinary cross-container move, by contrast, is
one semantic `onItemMove` transaction rather than an item-remove event followed
by an item-insert event.

## Every Drag Is a Session

A `DragSession` is the temporary state SnapSort creates for one drag gesture.
It lives on the root container while the drag is active and keeps track of
the drag-and-drop life cycle. Locations carried by an event describe the
source, prospective target, or final destination; they do not necessarily
identify the container whose callback is running.

The exported `DragSession` is a type-only, read-only handle. Every callback
for a gesture and `root.dragSession` observe the same handle; nested containers
return `null`. You can read `root`, `pointerId`, `items`, `sources`,
`pressedItem`, `primaryItem`, `start`, `pointer`, and `status`. The item/source
arrays, locations, and coordinates cannot be mutated. SnapSort keeps lifecycle
operations, target state, strategies, ghosts, and animation bookkeeping
internal.

During `onDragStart`, set `session.dragVisual` to choose whether the actual
`"item"`, a passive `"preview"`, or `"none"` follows the pointer. This is
independent from the mode's target resolver and placement feedback.
You may also set `dropEffect` to `"move"` or `"none"` while the session is
pending or active. `handoff(replacements)` is pending-only.
