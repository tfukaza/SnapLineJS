`Container` groups `Item` components into a sortable region and manages their
drag session. Every container must be rendered inside an `Engine`.

Start with the interactive
[Container basics](/docs/snapsort/examples/basics#basic-container), then use
[Container Recipes](/docs/snapsort/examples/containers) for focused examples
of each major prop and composition pattern.

## Component Properties

```ts
type ContainerProps = Omit<HTMLAttributes<HTMLDivElement>, "children"> & {
  children?: Snippet;
  config?: ContainerConfig;
  itemId: string;
  container?: SnapSortContainer | null;
  locked?: boolean;
  selected?: boolean;
  className?: string;
  metadata?: ItemMetadata;
};
```

There are no collection-specific `items`, `getItemId`, `entry`, `before`, or
`after` props. The application writes one ordinary children body and decides
where its keyed loop sits among fixed markup.

### `children`

`Container` renders ordinary optional children. Put fixed markup and the
application-owned keyed entries loop exactly where they belong in that body.

See [Rendering a Collection](/docs/snapsort/examples/containers#rendering-a-collection)
for an interactive example.

### `config`

`config` changes the container's sorting behavior. The most prominent
configuration is `direction`, which sets the main layout direction.

See [Changing Container Behavior](/docs/snapsort/examples/containers#changing-container-behavior)
for an interactive example and [Configuration](#configuration) for every
option.

### `bind:container`

`bind:container` is the one optional imperative handle. Use it when a button,
keyboard command, or other control needs to call the core API directly. The
bound value may be `undefined` or `null` until the component mounts and becomes
`null` when it unmounts. Declarative RenderTree rendering does not need a binding:
the reducer recognizes its root from the callback event and locates nested
logical trees through each Container's immutable `itemId`.

`moveItem` requests a move but does not take ownership of the rendered
collection. The root callback must still update Svelte state synchronously.
See [Programmatic Cross-Container Moves](/docs/snapsort/examples/containers#programmatic-cross-container-moves)
for the complete interaction.

> [!WARNING]
> Containers that need to interact must share one root `Container`. Drop-policy
> callbacks can filter destinations inside that tree; they cannot connect
> otherwise independent roots.

### `itemId`, `locked`, and `selected`

A `Container` can itself be an entry in a parent container. Give that nested
container an `itemId`, then set `locked={false}` to let it drag. `locked` defaults
to `true`, which is safer for containers that only organize child items.

Identity comes only from the required `itemId` prop. It must be non-empty,
cannot change while mounted, and must match an adopted core Container.
`metadata.itemId` is unsupported and throws a clear error.

`selected` is a consumer-owned flag. Dragging one selected entry moves the other
selected entries with it; your interface remains responsible for the selection
controls and state. See [Nested Containers](/docs/snapsort/examples/containers#nested-containers)
for the complete pattern.

### `class`, `className`, `style`, and HTML attributes

`Container` renders a `div`, so standard div attributes such as `aria-label` and
`data-*` pass through. Both Svelte's `class` prop and the cross-framework
`className` alias are merged with SnapSort's own classes; `style` is appended to
the layout styles SnapSort needs.

See [Container Presentation and HTML Attributes](/docs/snapsort/examples/containers#container-presentation-and-html-attributes)
for an interactive example.

## Direct Children and Render Entries

Fixed content is ordinary markup before or after the keyed sortable loop. It is
never registered as a SnapSort Item.

Use `entry.itemId` directly as the keyed loop's reconciliation identity.
SnapSort keeps ordinary Items, nested Containers, and live ghosts unique across
one root, so no second render-key domain or prefix is needed.

See [Fixed Content Around Items](/docs/snapsort/examples/containers#fixed-content-around-items)
for a collection surrounded by application controls and static markup.

The adapter does not keep private ghost state. A `RenderTree` node owns one
`entries` sequence containing ordinary values and ghosts. Root
`onGhostInsert`, `onGhostMove`, and `onGhostRemove` callbacks may all delegate
to `reduceRenderTree`; the callbacks stay explicit even when they share one
application function. SnapSort owns the ghosts' presence, so it must tell the
application when a ghost appears, when the same keyed ghost changes location
or insertion-gap presentation, and when it disappears. A presentation-only
insertion update carries equal `from` and `to` locations.

An ordinary move is intentionally different: `onItemMove` describes the whole
semantic transition, including its source and destination and every selected
item. It does not also emit item remove and insert events. Application-created
and application-deleted ordinary values do not require callbacks at all; edit
the RenderTree and let Svelte mount or unmount the matching component.

Item IDs must be unique across one RenderTree root, including the root
Container, nested Containers, ordinary Items, and live ghosts. Independent
roots may reuse IDs. The root component must stay mounted for the lifetime of
its RenderTree state. If it is destroyed, discard that state and create a new
tree for the replacement root.

See [Custom Ghost Rendering](/docs/snapsort/examples/containers#custom-ghost-rendering)
for an interactive renderer. The [Drags and Ghosts guide](/docs/snapsort/guides/sessions/ghosts)
defines the closed `GhostState` union, the geometry each role carries, and
which ghosts participate in flow.

Use `createRenderTree` and `reduceRenderTree` for the opinionated state shape,
or omit them and implement the explicit callbacks for another application
model:

```svelte
<script lang="ts">
  import {
    createRenderEntry,
    createRenderTree,
    reduceRenderTree,
    type ContainerCallbacks,
    type GhostLifecycleEvent,
    type ItemMoveEvent,
  } from "@snap-engine/snapsort";
  import { rejectDrop } from "@snap-engine/snapsort/callbacks";
  import { Container, Ghost, Item } from "@snap-engine/snapsort/svelte";

  type BoardValue =
    | { kind: "column"; title: string }
    | { kind: "task"; label: string };

  const taskEntry = (id: string, label: string) =>
    createRenderEntry<BoardValue>({ kind: "task", label }, id);

  let board = $state.raw(
    createRenderTree<BoardValue>([
      createRenderEntry(
        { kind: "column", title: "To do" },
        "todo",
        createRenderTree([
          taskEntry("task-1", "Sketch layout"),
          taskEntry("task-2", "Wire behavior"),
        ]),
      ),
      createRenderEntry(
        { kind: "column", title: "Done" },
        "done",
        createRenderTree(),
      ),
    ]),
  );

  function onItemMove(event: ItemMoveEvent) {
    board = reduceRenderTree(board, event);
  }

  function onGhostMove(event: GhostLifecycleEvent) {
    board = reduceRenderTree(board, event);
  }

  const callbacks = {
    onItemMove,
    onGhostInsert: onGhostMove,
    onGhostMove,
    onGhostRemove: onGhostMove,
    getDropPriority: rejectDrop,
  } satisfies ContainerCallbacks;
</script>

<Container itemId="project-board-root" config={{ callbacks }}>
  <header>Project board</header>

  {#each board.entries as entry (entry.itemId)}
    {#if entry.isGhost}
      <Ghost ghost={entry.ghost} />
    {:else if entry.childTree}
      <Container
        itemId={entry.itemId}
      >
        {#if entry.value.kind === "column"}
          <h2>{entry.value.title}</h2>
        {/if}

        {#each entry.childTree.entries as child (child.itemId)}
          {#if child.isGhost}
            <Ghost ghost={child.ghost} />
          {:else if child.childTree}
            <!-- Repeat this branch or extract an application-local recursive component. -->
          {:else if child.value.kind === "task"}
            <Item itemId={child.itemId}>{child.value.label}</Item>
          {/if}
        {/each}
      </Container>
    {:else if entry.value.kind === "task"}
      <Item itemId={entry.itemId}>{entry.value.label}</Item>
    {/if}
  {/each}

  <footer>Board controls</footer>
</Container>
```

The outer container is the root and owns structural callbacks. The inner list
containers receive no structural callbacks; they may still configure policy,
geometry, or hover callbacks. `rejectDrop` keeps tasks out of the board's top
level while the child trees remain eligible destinations. Moving a Container
entry carries its complete `childTree`; its immutable `itemId` keeps the same
mounted Container when the keyed loop moves it.

`reduceRenderTree` accepts `ItemMoveEvent`, `ItemSwapEvent`, `ItemRemoveEvent`,
and the three ghost lifecycle events. Those events completely describe the
next state of existing application entries. It deliberately does not accept
`ItemInsertEvent`: that event identifies a new core Item and its location but
cannot provide the application value to store in `RenderEntry<T>`. An advanced
`onItemInsert` integration must resolve that value and edit its own state.

### Application-owned item lifetime

An Add button or Delete button should edit the application-owned entries
directly. Here the board updates one nested child tree while preserving that
tree's entries:

```ts
function addTaskToTodo(id: string, label: string) {
  board = {
    ...board,
    entries: board.entries.map((entry) =>
      !entry.isGhost && entry.itemId === "todo" && entry.childTree
        ? {
            ...entry,
            childTree: {
              ...entry.childTree,
              entries: [...entry.childTree.entries, taskEntry(id, label)],
            },
          }
        : entry,
    ),
  };
}

function deleteTasksFromTodo(itemIds: readonly string[]) {
  const deleted = new Set(itemIds);
  board = {
    ...board,
    entries: board.entries.map((entry) =>
      !entry.isGhost && entry.itemId === "todo" && entry.childTree
        ? {
            ...entry,
            childTree: {
              ...entry.childTree,
              entries: entry.childTree.entries.filter(
                (child) => child.isGhost || !deleted.has(child.itemId),
              ),
            },
          }
        : entry,
    ),
  };
}
```

These are application functions, not SnapSort helpers. Svelte reconciles the
loop, and mounting or unmounting `Item` synchronizes the core registration. A
drop-to-trash interface follows the same ownership rule: set
`session.dropEffect = "none"` for the trash target, then delete all
`event.itemIds` from application state only if `onDragEnd` reports the trash as
its final `destination`. See
[Give a Drop Application Meaning](/docs/snapsort/examples/advanced-settings-and-callbacks#give-a-drop-application-meaning)
for a recursive, cancellation-safe recipe.

The imperative command is a separate direction of synchronization. If code
calls a core Container's `removeItem(id)`, SnapSort removes it from the core
tree and emits root `onItemRemove`. Add that callback and reduce it
synchronously:

```ts
import type {
  Container as SnapSortContainer,
  ItemRemoveEvent,
} from "@snap-engine/snapsort";

function onItemRemove(event: ItemRemoveEvent) {
  board = reduceRenderTree(board, event);
}

const callbacksWithCoreRemove = {
  onItemMove,
  onItemRemove,
  onGhostInsert: onGhostMove,
  onGhostMove,
  onGhostRemove: onGhostMove,
} satisfies ContainerCallbacks;

function removeThroughSnapSort(source: SnapSortContainer, itemId: string) {
  source.removeItem(itemId);
}
```

Use this imperative path only when SnapSort's core command is intended to lead
the change. Do not call it after already deleting the same entry from Svelte
state, and do not expect `onItemRemove` for the source half of a move.

## Configuration

| Option          | Default                        | Description                                                                                                     |
| --------------- | ------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| `mode`          | `"euclidean"`                  | Drag/drop mode for this tree: `"euclidean"`, `"progressive"`, `"insertion"`, or `"swap"`.                       |
| `direction`     | `"column"`                     | Main layout direction: `"column"` or `"row"`.                                                                   |
| `mainAxisAlign` | `"start"`                      | Main-axis alignment for virtual placement. Supports `"start"` and `"center"`.                                   |
| `wrap`          | `"auto"`                       | Infers wrapping from measured layout; `"nowrap"` keeps one visual line along the main axis.                     |
| `stretchItems`  | `false`                        | Sizes entries to the destination's cross axis, analogous to CSS `align-items: stretch`.                         |
| `name`          | Generated                      | Human-readable container name.                                                                                  |
| `animation`     | `undefined`                    | Optional reorder, drop, and programmatic-move animation settings. Omit it or set it to `null` for no animation. |
| `dropPriority`  | `0`                            | Base destination policy: `-1` rejects; nonnegative values rank candidates, with higher values considered first. |
| `callbacks`     | No persistent mutation default | Root handlers for SnapSort-originated structure/lifecycle plus local policy, geometry, and hover hooks.         |

Animations are opt-in. Use SnapSort's standard 100ms preset when you want the
library's conventional motion:

```svelte
<script lang="ts">
  import { defaultAnimations } from "@snap-engine/snapsort";
</script>

<Container itemId="animated-list-root" config={{ animation: defaultAnimations }} />
```

Mode is resolved from the root container when a drag starts, so nested containers in one drag tree should use the same mode.

## Callbacks

Callbacks have two explicit ownership rules.

Structural and lifecycle callbacks resolve on the **tree root**. Put them only
in the root `Container`'s config; descendant structural callbacks are rejected.
The event payload identifies the semantic containers, so one root handler can
route state for the entire tree.

| Root callback                        | Meaning                                                                                                                          |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| `onItemMove(event)`                  | Preferred persistent move. `from` and `to` identify the source and destination; the source does not also receive `onItemRemove`. |
| `onItemInsert(event)`                | Lower-level core insertion and fallback when `onItemMove` is absent; framework mounting does not emit it.                        |
| `onItemRemove(event)`                | Core `removeItem` command, not application-state unmounting or the source half of a move.                                        |
| `onItemSwap(event)`                  | One atomic pairwise exchange; required for swap mode in Svelte.                                                                  |
| `onGhostInsert/Move/Remove(event)`   | Explicit presence and relocation commands carrying `event.ghost`; an application may pass each one to `reduceRenderTree`.        |
| `onDragStart/End(event)`             | Root lifecycle. Start may veto or choose `dragVisual`; end reports the final outcome.                                            |
| `onDropTargetChange(event)`          | Reports a changed prospective destination.                                                                                       |
| `onVisualGeometryInvalidated(event)` | Coalesced notification for dependent visuals after drag, ghost, FLIP, or settle geometry changes.                                |

The following callbacks remain **per container** because they answer policy,
geometry, or hover questions about that direct container:

| Local callback               | Owner                                   |
| ---------------------------- | --------------------------------------- |
| `getDropPriority`            | Each candidate destination.             |
| `getItemHitbox`              | The direct owner of the candidate item. |
| `onDragItemEnter/Move/Leave` | The direct owner of `event.overItem`.   |

Root structural callbacks run inside the root adapter's synchronous commit.
Policy, geometry, and hover callbacks run directly. Missing framework
structural callbacks fail clearly; SnapSort never falls back to Vanilla DOM
mutation for a Svelte-owned tree.

### Drag visuals

`DragSession.dragVisual` separates pointer representation from placement mode:

```svelte
<Container
  itemId="insertion-list-root"
  config={{
    mode: "insertion",
    callbacks: {
      onDragStart: (event) => {
        event.session.dragVisual = "preview";
      },
    },
  }}
>
</Container>
```

The choices are `"item"`, `"preview"`, and `"none"`. A preview is one
root-owned `pointer-preview` ghost for the complete dragged run; insertion's
destination remains a separate `insertion-marker` ghost. Both appear in their
owning tree node's `entries` sequence and render through `Ghost`. Set the
property only while the session is pending, normally in `onDragStart`.

### Insertion marker geometry and item hitboxes

SnapSort owns insertion targeting geometry. The `insertion-marker` state
contains a zero-thickness world-space `gap`, frozen `previous` and `next`
neighbors for the chosen physical boundary, and `isCurrentPlacement`. Marker
paint is deliberately separate from candidate ranking.

The insertion-specific part of the public state is:

```ts
interface InsertionMarkerState {
  readonly type: "insertion-marker";
  readonly location: GhostSlotLocation;
  readonly gap: InsertionGapSegment;
  readonly previous: InsertionMarkerNeighbor | null;
  readonly next: InsertionMarkerNeighbor | null;
  readonly isCurrentPlacement: boolean;
  // Plus the shared GhostState identity and dragged-run fields.
}
```

Each neighbor contains its exact `Item`, `itemId`, frozen metadata, and frozen
world-space border rectangle. A nested `Container` is also an `Item`, so no
separate container-neighbor variant is needed.

The built-in `Ghost` has an explicit 3px stock presentation. Pass all three
marker options when the product needs another rectangle:

```svelte
<script lang="ts">
  import {
    type GhostState,
    type InsertionMarkerRectOptions,
  } from "@snap-engine/snapsort";
  import { Ghost } from "@snap-engine/snapsort/svelte";

  let { ghost }: { ghost: GhostState } = $props();

  const markerOptions = {
    thickness: 2,
    startInset: 24,
    endInset: 8,
  } satisfies InsertionMarkerRectOptions;

</script>

{#if ghost.type === "insertion-marker"}
  <Ghost {ghost} insertionMarker={markerOptions} />
{:else}
  <Ghost {ghost} />
{/if}
```

Custom renderers and adapters use the same pure conversion instead of
reimplementing coordinate projection:

```ts
import { insertionMarkerRect } from "@snap-engine/snapsort";
import type { InsertionMarkerState } from "@snap-engine/snapsort";

function renderMarker(marker: InsertionMarkerState, element: HTMLElement) {
  const rect = insertionMarkerRect(marker, markerOptions);
  element.style.left = `${rect.x}px`;
  element.style.top = `${rect.y}px`;
  element.style.width = `${rect.width}px`;
  element.style.height = `${rect.height}px`;
}
```

`startInset` means left for a horizontal line and top for a vertical line;
`endInset` means right or bottom. Insets and thickness alter only rendering.
Both insets must be non-negative and their sum must not exceed `gap.length`.
The returned rectangle is relative to `ghost.location.container`, including
its border and scroll offset, and is ready for absolute positioning.

`toContainerLocalRect(worldRect, container)` exposes the same border-, scroll-,
and camera-aware projection for another world-space overlay. Vanilla can keep
the stock adapter and choose marker presentation with
`createVanillaAdapter({ insertionMarker: markerOptions })`.

`getItemHitbox` remains a direct-container geometry callback because its return
value intentionally changes hover/swap targeting. It receives the dragged
item, candidate `overItem`, direct owner, pointer, and frozen `defaultRect`.
Return either `{ shape: "rect", rect }` or
`{ shape: "circle", center, radius }`.

- Configure persistent and ghost structural callbacks once on the root.
  Their event locations route updates to the source and destination records.
- Configure `onItemSwap` on the root of every swap tree.
- Keep priority, item-hitbox geometry, and hover callbacks on the
  direct containers whose behavior they customize.

Configure `onItemRemove` when application code can invoke `removeItem(id)`, and
pass it through `reduceRenderTree` when using RenderTree state. Direct
application-state deletion needs no callback. Ordinary moves emit only the
root-dispatched `onItemMove`/`onItemInsert` event.

Update Svelte state synchronously in every structural callback. The adapter
uses its root `commit` boundary and `flushSync`, allowing SnapSort to read final
DOM geometry before paint. Missing callbacks fail clearly instead of mutating
framework-rendered DOM.

### Drop policy events

Drop targeting resolves one effective policy value, then runs the selected
placement mode. `DropPriorityEvent` includes `itemMetadata`/`itemsMetadata`,
destination `containerMetadata`, the primary `source`, `sources` parallel to
the full multi-item drag, `staticPriority`, the representative `index`, pointer
and frozen rectangle geometry, and destination depth. Effective `-1` rejects;
nonnegative values rank candidates owned directly by this Container and do not
propagate to nested Containers.

See [Standard Callbacks](/docs/snapsort/reference/callbacks) for exact
resolution rules and reusable policies from
`@snap-engine/snapsort/callbacks`.

## Core Object API

After capturing the object with `bind:container`, these are the most commonly
used core properties and methods.

| API                                              | Description                                                                                                  |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| `container.moveItem(id, targetContainer, index)` | Authoritatively moves an item into another container or index, bypassing drop policy.                        |
| `container.removeItem(id)`                       | Removes an item from the core tree and emits root `onItemRemove`; framework state must update synchronously. |
| `container.numberOfItems`                        | Number of tracked child items.                                                                               |
| `container.dropPriority`                         | Gets or sets the base policy: `-1` rejects; nonnegative values rank the Container.                           |
| `container.direction`                            | Gets or sets `"column"` or `"row"`.                                                                          |
| `container.mainAxisAlign`                        | Gets or sets `"start"` or `"center"`.                                                                        |
| `container.mode`                                 | Gets or sets the drag/drop mode.                                                                             |
| `container.config`                               | Live `ContainerConfig` object.                                                                               |
| `container.callbacks`                            | Configured callback object.                                                                                  |
| `container.dragSession`                          | Stable read-only `DragSession` handle on the root container while active; nested containers return `null`.   |
